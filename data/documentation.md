# Bombay Shaving Company AI Sales Representative

## Technology

### Backend

- Python
- FastAPI
- LangChain
- LangGraph
- Neon PostgreSQL
- `pgvector` for embedding storage and similarity search
- Mistral AI / Hugging Face models and embeddings

### Frontend

- React
- `react-markdown` for Markdown rendering

### Architectural Principle

LangChain will be used as the abstraction layer for model, embedding, and retrieval integrations. LangGraph will handle workflow orchestration.

Business logic will remain in normal Python code. SQL queries, metadata filtering, product-card creation, and validation will not be hidden inside LLM prompts.

The code structure, folder structure, API paths, and implementation details will be finalized during backend development.

## Documentation Structure

This document has two parts:

- **System Flow:** Sections 1–9 describe how a user request moves through the application and becomes a frontend response.
- **Data Architecture:** The final section describes the datasets, database responsibilities, embedding sources, and retrieval approach that support the system flow.

The Data Architecture section is separate from the runtime flow. The datasets are used by the relevant nodes, but they are not additional processing nodes in the request pipeline.

## 1. User Query

For the MVP, the frontend will send the user's message and the conversation ID to the backend.

### Request

```json
{
  "message": "What products do you have for hair care?",
  "conversation_id": "guest_8c36b3ac-4a1e-48be-9ce0-a00ac43b7e4c"
}
```

### Fields

#### `message`

The natural-language message entered by the user.

#### `conversation_id`

Identifies the conversation and allows the backend to maintain context across messages.

## 2. Conversation State / Session Loader

For the MVP, users are treated as guests and no long-term user history is maintained.

When a conversation starts, a conversation state is created and associated with the `conversation_id`. For every new message, the session loader retrieves the existing conversation state, including the relevant chat history and context, and makes it available to the LangGraph workflow.

The conversation state will grow as the workflow is finalized. It may later include information such as detected intent, user messages, assistant responses, and other data generated by the workflow nodes.

When the system asks for clarification, the session state stores the pending clarification so the next user message can be interpreted correctly:

```json
{
  "pending_clarification": {
    "original_query": "Suggest a trimmer",
    "intent": "recommendation",
    "missing_field": "use_case",
    "question": "What will you mainly use the trimmer for: beard grooming, body grooming, or both?",
    "attempt_count": 1
  }
}
```

If the next message is an unrelated new request, the pending clarification is discarded and the new request starts normally.

The amount of conversation history passed to the LLM will be finalized separately. The system should retrieve the relevant history for the current request rather than automatically passing all stored conversation data to every node.

Session expiry and removal of inactive conversation data may be considered after approximately 10–15 minutes of inactivity. The detailed expiry behavior will be defined later.

## 3. Query Understanding

Query Understanding converts the user's message and relevant conversation state into structured information that downstream nodes can use.

For the MVP, the output should remain simple and flexible:

```json
{
  "intent": "recommendation",
  "scope": "in_scope",
  "entities": {},
  "filters": {},
  "context": {}
}
```

### Intents

The initial intent categories are:

```text
recommendation
comparison
knowledge
support
```

### Scope

The `scope` field identifies whether the request is related to Bombay Shaving Company products, grooming guidance, or support information.

```text
in_scope
out_of_scope
```

An `out_of_scope` value routes the request to the Out-of-Scope Handler. It is not one of the four specialist intents.

The `knowledge` intent includes product information, usage instructions, explanations, categories, ingredients, and general grooming questions.

### Output Fields

#### `intent`

Represents what the user wants from the system.

#### `scope`

Represents whether the request is relevant to the BSC assistant and determines the initial routing path.

#### `entities`

Contains the relevant things mentioned by the user, such as products, categories, use cases, body areas, or attributes.

#### `filters`

Contains user constraints and preferences, such as budget, skin type, hair type, required features, or exclusions.

#### `context`

Contains relevant information carried from the conversation, such as previously mentioned products or preferences.

Example:

```json
{
  "intent": "recommendation",
  "entities": {
    "category": "trimmer",
    "use_case": ["body_grooming"]
  },
  "filters": {
    "budget_max": 2000
  },
  "context": {
    "previously_mentioned_product_ids": []
  }
}
```

### Responsibility Boundary

Query Understanding identifies what the user is asking and extracts the information they provided. It does not generate the final answer or decide whether the query contains enough information to proceed.

It should use conversation state to resolve references such as “this product.” Product names may be extracted at this stage, while exact product matching can happen during retrieval.

Empty fields are acceptable when the user has not provided the corresponding information.

## 4. Sufficiency Check

The Sufficiency Check determines whether the structured query contains enough information to produce a useful response for the identified intent.

### Flow

```text
Conversation State / Session Loader
        ↓
Query Understanding
        ↓
Sufficiency Check
   ├── Sufficient → Specialist Node
   └── Insufficient → Clarification Node → response to the user
```

If the query is insufficient, the Clarification Node generates a focused clarification question and returns it to the user.

When the user sends the next message, the system uses the conversation history and Query Understanding to determine whether the message answers the pending clarification or represents a new request.

```text
User's next message
        ↓
Query Understanding
   ├── Answers clarification → merge with original query → Specialist Node
   └── New request → Sufficiency Check
```

No follow-up flag is required in the frontend request. The system identifies clarification responses using the existing conversation history and the new user message. This keeps the request limited to `message` and `conversation_id`.

The Sufficiency Check should not repeatedly ask clarification questions for the same request. If the user provides a new request, it should be processed as a new query.

## 5. Specialist Layer

The Specialist Layer contains modular intent-specific nodes that process the structured output from Query Understanding. Each specialist retrieves the information it needs from the appropriate BSC data source and returns structured results to the Composer.

For the MVP, the Specialist Layer includes:

1. `recommendation`
2. `comparison`
3. `knowledge`
4. `support`

Each specialist should retrieve and prepare information for the Composer rather than generate the final conversational response.

### Recommendation Specialist

Handles product recommendations based on the user's needs, preferences, and filters.

Primary data sources:

- Product database
- Product search content or embeddings
- Relevant knowledge content when required

### Comparison Specialist

Compares two or more products using their available product information and structured fields.

Primary data source:

- Product database
- Product search content or embeddings

### Knowledge Specialist

Handles product information, usage questions, explanations, and general grooming knowledge.

Primary data sources:

- BSC blog/content data
- Relevant product information

### Support Specialist

Handles support-related questions using available FAQs, policies, and customer-care information.

Primary data sources:

- Support FAQs
- Return, refund, and shipping policies
- Customer-care information

For the MVP, the Support Specialist cannot verify customer-specific order status, delivery dates, refund status, or actual order contents because live support and order-management APIs are not yet available. It should provide only general guidance based on the available support data and direct the user to customer care when specific account or order information is required.

### Multiple Specialists

A query may require more than one specialist. For example, a request to recommend a face wash for oily skin and explain how to use it may require both the Recommendation Specialist and the Knowledge Specialist.

The Composer will receive the structured results from the selected specialists and generate the final response.

### Specialist Output

All specialists should return a common outer structure, while the contents of `data` may differ by specialist.

```json
{
  "specialist": "recommendation",
  "status": "success",
  "data": {},
  "sources": [],
  "warnings": []
}
```

This common structure allows the Composer to consume specialist results without needing to know the internal retrieval or processing logic of each specialist.

## 6. Composer

The Composer is the presentation layer of the workflow. It converts structured results from one or more specialists into a user-friendly response that can be rendered by the frontend.

The Composer should:

- Use Markdown for normal user-facing content.
- Return Markdown compatible with the frontend's [`react-markdown`](https://www.npmjs.com/package/react-markdown) renderer.
- Return structured UI data only when the frontend needs a specific component.
- Use only information provided by the specialist results.
- Not retrieve data or decide which products, comparisons, or facts are correct.

### Response Structure

Every response should follow a consistent structure:

```json
{
  "type": "recommendation",
  "markdown": "User-facing Markdown response",
  "product_tray": [],
  "metadata": {
    "specialists_used": [],
    "sources": []
  }
}
```

### Response Types

#### Recommendation

Returns a Markdown explanation and a structured `product_tray` for rendering product cards.

```json
{
  "product_id": "trimmer_001",
  "name": "Product A",
  "price": 1799,
  "image_url": "https://...",
  "product_url": "/products/product-a"
}
```

The product tray must contain only products included in the Recommendation Specialist's result.

#### Comparison

Returns the comparison as Markdown. A Markdown table is sufficient for the MVP; a separate frontend comparison structure is not required initially.

#### Knowledge

Returns a properly formatted Markdown explanation based on the Knowledge Specialist's result.

#### Support

Returns clear Markdown guidance based on the Support Specialist's result. The Composer must not claim customer-specific order status, delivery dates, refund status, or order verification without data from a future support or order-management API.

#### Clarification

Returns the clarification question as Markdown with an empty `product_tray`.

### Composer Rules

The Composer must not introduce unsupported product names, prices, features, policies, or URLs. It should keep the response clear and concise, and keep product IDs, image URLs, and product URLs in structured fields rather than relying on Markdown text.

For non-recommendation responses, `product_tray` should be empty.

## 7. Validator

The Validator checks whether the Composer's response is consistent with the structured output returned by the Specialist Layer.

For the MVP, validation remains lightweight and deterministic. It does not make additional API calls, use another LLM, or perform detailed sentence-level fact checking.

### Validation Checks

The Validator checks:

- The response structure and response type.
- Product data in the product tray against the Recommendation Specialist output.
- Comparison values against the Comparison Specialist output.
- Support information against the Support Specialist output.
- That the Composer has not added unsupported structured information.

The Specialist output remains the source of truth. The Composer formats that information, and the Validator checks the consistency between them.

### Validation and Revision Flow

Validation checks are divided into critical and non-critical checks.

Critical checks include:

- Product IDs, names, prices, image URLs, and product URLs match the Specialist output.
- Comparison values match the Comparison Specialist output.
- Support contact and policy information matches the Support Specialist output.
- The response structure is valid.

Non-critical checks include Markdown formatting quality, optional product badges, optional source metadata, and minor wording or formatting issues.

```text
Specialist Output
        ↓
Composer
        ↓
Validator
   ├── No critical failures → Response Envelope
   └── Critical failure → Composer runs one more time
                              ↓
                            Validator
                              ├── Valid → Response Envelope
                              └── Still invalid → Fallback response
```

When a critical failure occurs, the Composer receives the original Specialist output, the previous response, and the validation issues. It generates one revised response.

The system does not retry again. If the revised response still has a critical failure, the system returns a `fallback` response rather than knowingly returning mismatched product, comparison, or support information.

## 8. Response Envelope

The Response Envelope is the final API wrapper returned to the frontend. It packages the validated response into a stable and consistent format.

It does not contain AI logic, retrieval logic, composition logic, or validation logic.

### MVP Response Structure

```json
{
  "success": true,
  "conversation_id": "guest_abc123",
  "response": {
    "type": "recommendation",
    "markdown": "## Recommended options",
    "product_tray": [],
    "suggested_prompts": []
  },
  "error": null
}
```

### Fields

- `success`: Indicates whether the request was processed successfully.
- `conversation_id`: Identifies the guest conversation.
- `response.type`: Identifies the response category.
- `response.markdown`: Contains the user-facing Markdown response rendered by the frontend using `react-markdown`.
- `response.product_tray`: Contains structured product-card data when required; otherwise, it is an empty array.
- `response.suggested_prompts`: Contains optional suggested questions for clarification or out-of-scope responses.
- `error`: Is `null` for a successful response.

The initial response types are:

```text
recommendation
comparison
knowledge
support
clarification
out_of_scope
fallback
```

For non-recommendation responses, `product_tray` should be empty. `suggested_prompts` is optional and is used only when the response needs to guide the user toward a useful next question.

The final processing boundary is:

```text
Validator → Response Envelope → Frontend
```

The Response Envelope only packages the validated result into the frontend API contract.

A fallback response is used only when a critical validation failure remains after the single Composer revision attempt.

```json
{
  "type": "fallback",
  "markdown": "I’m unable to verify the exact details right now. Please try again or ask about a specific product or category.",
  "product_tray": [],
  "suggested_prompts": [
    "Suggest a trimmer for body grooming",
    "Compare two trimmers"
  ]
}
```

## 9. Clarification and Out-of-Scope Handlers

Clarification and out-of-scope responses are handled separately from the four Specialist Nodes. They guide the conversation toward a valid BSC-related request and do not require product, blog, or support retrieval.

### Flow

```text
Conversation State
        ↓
Query Understanding
   ├── Out of scope → Out-of-Scope Handler → Response Envelope
   └── In scope
          ↓
      Sufficiency Check
          ├── Insufficient → Clarification Handler → Response Envelope
          └── Sufficient → Specialist Node → Composer → Validator
```

### Clarification Handler

When the Sufficiency Check determines that the query is insufficient, the Clarification Handler generates one focused question about the most important missing information.

The response uses `type: "clarification"`, contains Markdown, has an empty `product_tray`, and may include one or more `suggested_prompts`.

The clarification is retained in the conversation history. When the user sends the next message, Query Understanding determines whether it answers the clarification or represents a new request.

The system should not repeatedly ask clarification questions for the same request.

### Out-of-Scope Handler

When Query Understanding identifies a request unrelated to Bombay Shaving Company products, grooming guidance, or support information, the Out-of-Scope Handler returns a polite response explaining what the assistant can help with.

The response uses `type: "out_of_scope"`, contains Markdown, has an empty `product_tray`, and may include one or two relevant `suggested_prompts`.

Suggested prompts should come from a small predefined set of relevant BSC questions rather than being freely generated each time.

These handlers do not need the normal Specialist → Composer → Validator path for the MVP because they do not make product, comparison, knowledge, or support claims.

## Data Architecture

This section describes the data used by the MVP and how the runtime components access it. It is separate from the request-processing flow described in Sections 1–9.

### Data Sources and Retrieval

The MVP uses one canonical product dataset and three retrieval-oriented datasets.

### Data Sources

#### Canonical Product Data

`bombay-shaving-product-data.json` is the primary product dataset. It contains approximately 205 products and will be stored in a separate PostgreSQL product table.

This is the authoritative source for:

- Product details
- Prices
- Availability
- Product names and IDs
- Product images and URLs
- Comparison fields
- Product-card data

The current product file is a scraped snapshot that imitates the product source. If BSC provides an API later, the scraped source can be replaced without changing the overall workflow.

#### Enriched Product Data for Embeddings

`bombay-shaving-enriched-products-data-for-embeddings.json` contains enriched records for the same approximately 205 products. Product IDs match the canonical product dataset.

This dataset is used to create product embeddings. The main embedding content includes:

- Product name
- Category
- Product type
- Gender
- Short benefit summary
- Searchable text

Other fields can be stored as metadata for filtering and retrieval. The enriched embedding data is not the source of truth for prices, availability, or final product-card details.

#### Blog Data for Embeddings

`bsc-blogs-for-embeddings.json` contains BSC blog documents divided into chunks. Each chunk includes information such as the blog ID, title, category, heading, content, and URL.

The embedding content includes:

- Title
- Category
- Heading
- Chunk content

The URL is stored as metadata and does not need to be part of the embedding text. This dataset is used for knowledge and product-related questions, including product usage, grooming guidance, and concerns such as oily skin.

#### Support Data for Embeddings

`bsc-support-for-embeddings.json` contains FAQs and policies. Relevant fields such as questions, answers, topics, categories, and policy content are used to create support embeddings.

This dataset is used for support-related questions such as:

- Damaged or missing products
- Complaint and support requests
- Return and refund policies
- Shipping and delivery guidance

It does not provide live customer-specific order status or account information.

### Database Access

For the MVP, the backend will query PostgreSQL directly through a product repository or service layer. An additional internal API layer is not required.

The repository layer keeps the workflow independent from the current data source. It can use the PostgreSQL product table now and be replaced with a BSC API integration later if one becomes available.

### Retrieval Approach

The system will use a hybrid retrieval approach.

For recommendation queries:

```text
User query
    ↓
Query Understanding
    ↓
Semantic search over enriched product embeddings
    ↓
Candidate product IDs
    ↓
SQL lookup in the canonical product table
    ↓
Filtering, ranking, and complete product data
```

Semantic search is useful for understanding needs such as patchy beard grooming, beginner-friendly products, travel-friendly products, or sensitive skin. SQL is used for exact conditions and trusted product information such as price, category, availability, product details, URLs, images, and comparison fields.

For product information and comparison queries, direct SQL lookup may be sufficient. Knowledge queries use blog embeddings with relevant product data when required. Support queries use support embeddings.

### Embedding Record Separation

Embedding records should retain their source identity so the system can route and filter retrieval correctly. A common embedding record can contain:

```text
source_type: product | blog | support
source_id
content
metadata
embedding
```

The canonical PostgreSQL product table remains the source of truth for product information, while embeddings are used to discover relevant content and candidate product IDs.
